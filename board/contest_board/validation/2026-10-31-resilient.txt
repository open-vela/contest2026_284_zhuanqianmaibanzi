VelaPoka resilient candidate — 2026-10-31 Asia/Shanghai

Baseline evidence:
  User reports previous upload-fix now uploads normally; no Data glitch in
  the reported short test. New resilient behavior is not board accepted yet.

Implemented:
  Inspection result held 2 s, then LIVE resumes, boxes cleared, metrics kept.
  Explicit freeze/Stop/next capture/Finish/shutdown cancel the old UI timer.
  Up to 3 attempts per file; 300/600 ms cancellable backoff; reconnect/reopen
  before retry to avoid commands inside unfinished raw payloads.
  Permanent local/CRC failures logged; continue other images. Persistent
  network failure or untrusted manifest aborts instead of timing out for all
  remaining files. Missing images withhold new results.jsonl; INCOMPLETE.
  SD upload-errors.jsonl records uptime_ms/file/error, fsynced. PC device
  upload-journal.jsonl records UTC failure reports and batch summaries.
  PC rejects complete summaries without a confirmed results.jsonl.
  VKP2/OK2 version check rejects old receiver before uploading. New PC still
  supports legacy VKP1. Controlled LAN only, no TLS/authentication added.
  <=64 KiB files cached for one-pass SD read, CRC then transmit same snapshot.
  Cache allocation failure falls back to 4 KiB streaming/two passes.
  Timed io_lock waits in usage/export/failure-log paths: 3 s. Network idle
  waits ~30 s, connect ~3 s, send timeout 3 s, reply overall limit ~120 s even
  with WAITs. No claim of forcibly interrupting stuck underlying SD calls.
  Product default remains SPI 1 MHz. Separate velapoka_spi4m is experimental.
